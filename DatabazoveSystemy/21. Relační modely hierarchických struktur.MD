# Relační modely hierarchických struktur - Supertype/Subtype, příklady využití, modelování v DataModeleru, implementace v SQL

## Definice a princip Supertype/Subtype
- **Supertype**:
  - Obecná entita
  - Obsahující atributy apolečně pro všechy své podtypy
  - Např. entita osoba je Supertype a bude obsahovat `Jmeno`, `Prijmeni` a `Rodne_cislo`
- **Subtype**:
  - Specializovaná entita
  - Dědí všechny atributy od supertypu a přidává vlastní
  - Např. entita Student je Subtype a bude obsahovat všechno od Osoby + `Prumerna_znamka`,</br> entita Ucitel bude obsahovat vse od Osoby + `Akademicky_titul`

## Proces tvorby
- Generalizace (Zdola nahoru):
  - Máme Entity: `Auto`, `Motocykl` a `Nákladní vůz`
  - Všichni mají společné prvky (SPZ, Výrobce...)
  - Vytvoříme Supertype `Vozidlo`
- Specializace (Shora dolů):
  - Máme entitu `Zaměstnanec` a zjistíme, že potřebujeme evidovat specifická data
  - Např. `Externista`, `Brigádník`, `FullTime`

## Pravidla omezení
- Musíme definovat dvě základní vlastnosti, které určují jak se entity chovají
- Disjointness:
  - Disjoint (Rozpojené):
    - Instance nadtypu může patřit maximálně do jednoho podtypu
    - např. Student je buď prezenční nebo dálkový, nemůže být obojí najednou (Něco jako ARC)
  - Overlap:
    - Instance může patřit do více subtypů současně
    - Např. osoba může být v systému jako student i zam
- Completeness:
  - Mandatory / Total:
    - Každá instance Supertype musí patřit alespoň do jednoho subtypu
  - Optional / Partial:
    - Instance může existovat sama od sebe

## Modelování v nástroji Data Modeler
- V profesionálních CASE nástrojích se tato struktura modeluje pomocí speciálního vizuálního prvku
- Vytvoří se hlavní entita (Supertype)
- Vytvoří se podřízená entita Subtypes
- Použije se nástroj pro vytvoření Hierarchy nebo Subtype Box
- Důležitým prvkem je Subtype Discriminator - atr. v Supertypu, dle kterého db pozná o jaký subtype se jedná

## Implementace v SQL (Logický a fyzický model)
- Relační DB neumí nativně kreslit podtypy uvnitř tb
- Existují proto 3 strategie:
  - 1 Tabulka pro vše (Všechny subtypes a supertypes u sebe)
    - Výhody: velmi rychlé
    - Nevýhoda: Spusta hodnot NULL, plýtvání místem
  - Samostatné tabulky s vazbou 1:1
    - 1 Tabulka pro supertype a několik subtype tabulek
      - Implementace: Tabulky podtypů mají svůj PK, jejich FK odkazuje na tabulku SuperTypu
      - Výhody: Čistý designe, žádné zbytečné NULL hodnoty
      - Nevýhody: Musíme spojovat tabulky joiny
```sql
-- Příklad implementace Table-per-Type
CREATE TABLE osoba(
    id int not null identity(1,1) primary key,
    jmeno varchar(20),
    typ_osob char(1)
);

CREATE TABLE student(
    id int primary key,
    indexovani varchar(20),
    foreign key (indexovani) references osoba(id)
);
```

- Pouze tabuly SubTypu:
  - SuperType vubec neexistuje
  - Nevýhoda: Špatně se dělají dotazy
